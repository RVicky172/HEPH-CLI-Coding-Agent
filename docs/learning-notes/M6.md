# M6: Memory of the forge (context management + sessions), learning notes

**Goal:** long sessions keep working. Every request stays inside the model's context window, and you can continue tomorrow where you stopped today.

## The problem
An LLM has no memory: **every request re-sends the whole conversation** (system prompt + tool schemas + every message + every file it read). Your LM Studio model was loaded with a **18,688-token** window, and one question with tools already used about 5k. A few file reads and the request no longer fits: the server errors or silently cuts the beginning.

## The solution, cheapest first

```
before EVERY model call:
  ┌──────────────────────────────────────────────────────────────────────────┐
  │ 0. context ≥ 75% AND the old part is worth it?  → COMPACT (once per turn) │  persistent, 1 extra model call
  │    old turns ──(model writes a summary)──► [Summary of the earlier conv.] │
  ├──────────────────────────────────────────────────────────────────────────┤
  │ 1. FIT this request (non-destructive, the stored history is untouched):  │  free
  │    a) replace old tool outputs by "[older tool output removed…]"         │  (file contents can be re-read)
  │    b) still too big → leave out the oldest WHOLE turns                   │  (never split a tool call from its result)
  └──────────────────────────────────────────────────────────────────────────┘
after the call: calibrate the token estimate with the server's real count
```

| Piece | File | Idea |
|---|---|---|
| Token estimate | `core/context/TokenEstimator.ts` | ~3.6 chars/token, then **self-calibrating** from `usage.prompt_tokens` (EMA, clamped 0.5–3×). There's no per-model tokenizer to ship |
| Fit + compaction | `core/context/ContextManager.ts` | works on whole **turns** (user msg + everything until the next one), so the API rule "every tool call has a result" can't break |
| Summariser | `core/context/llmSummarizer.ts` | the same model, no tools, temperature 0.1, with a strict "keep paths, commands, results, open tasks" prompt |
| Window size | `OpenAICompatibleProvider.contextWindow()` | LM Studio's own REST API `GET /api/v0/models` → `loaded_context_length`. Config `profiles.*.contextWindow` overrides it. Defaults: 16k local, 128k cloud |
| Sessions | `sessions/SessionStore.ts` | `.heph/sessions/<id>.json`, write-then-rename (atomic), id validated (no `../`), git-ignored. The system prompt is NOT stored: it's rebuilt fresh on resume |

## New in the UI
- `ctx 23%` in the input box and the stats line (green → yellow at 60% → red at 85%)
- `/context`: bar chart of what uses the tokens (system prompt, tool schemas, conversation)
- `/compact`: summarise now
- `✻ compacted 3 older turns into a summary · 9.4k → 5.3k tokens`, and `✂ to fit the context: …`
- `heph -c` continues the latest session, `heph --resume <id>`, and `heph sessions` lists them

## Verified with the real model (window forced to 8k via config)
Read 3 whole files (≈3.3k tokens each) in 3 turns, then "which secret words have you found?". heph shortened, dropped and compacted, and the model **still listed all three correctly from the summary**. A *new process* with `heph -c` then answered "we extracted secret words from three files". The token estimate matched the server's count within a few percent.

## Bugs found by that real run
1. **A second compaction in the same turn: "9.4k → 9.4k".** No gain, and it cost an extra ~30 s model call on a local model. Fix: at most one compaction per turn, and only when the old part is ≥ 15% of the budget.
2. **"ctx 174%".** It measured the whole *stored* history, not what is *sent* after fitting. Fix: report the fitted size.
3. **Resumed title "[Summary of the earlier conversation] …".** After compaction the first user message *is* the summary. Fix: the title is fixed at the first save and skips summaries.
4. The `✂` notice repeated on every step. Now it shows only when something new was trimmed.

**Lesson:** unit tests proved the mechanics. Only a *real* constrained run showed the cost/benefit problems (slowness, useless work, confusing numbers).

## Trade-offs to understand
- **Summaries lose detail.** That's why tool outputs are elided first (re-readable) and summarising is the second step.
- **Compaction costs a model call.** On a local 30B model that's 20–40 s. It's worth it only when it frees real space.
- **Estimates are not exact.** Qwen's chat template adds hidden tokens for tools. Calibration absorbs that after the first request.
- **Resumed sessions forget which files were read.** The read-before-edit rule then forces fresh reads. That's intentional, since files may have changed.

## Exercises
1. Add `/sessions` inside the chat to switch sessions without restarting.
2. Make `compactAt` and `keepRecentTurns` configurable (`"context": { "compactAt": 0.8 }`).
3. Use `js-tiktoken` for OpenAI profiles and compare its counts with the estimate.
4. Summarise *incrementally*: fold only the oldest un-summarised turn into the existing summary.
